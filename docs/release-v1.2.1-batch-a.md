## 1. 建议执行顺序（不是按编号）

```
并行轨 1（同步层，必须串）：  D5 ──▶ D6 ──▶ D3 ──▶ D4 ──▶ D8
并行轨 2（独立小修）：        X1    X2 ──▶ D7    X3
并行轨 3（详情页，同文件）：  X4 ──▶ X5
并行轨 4（统计，独立）：      D1 ──▶ D2
```

理由：
1. **D5 先把同步的返回类型定型**（401/5xx/超时/404/412 进同一套类型），D3 判「登录失败 vs 远端真没数据」、D4 挑 412 都建立在它之上；反过来做要改两遍。

3. **D3 先于 D4/D8**：字段级合并没落地时，412 自动重合并等于白做；私密标记的覆盖修复也复用同一套合并。
4. **X2 先于 D7 或与 D7 同时裁决**：两者操作同一块 UI 与同一个偏好字段（见 §3 裁决 1）。

## 3. 三条需要拍板的裁决（我已给倾向）

**裁决 1：D7 与 X2 互斥，怎么办？**
X2 要删的两行 picker 正是源顺序的唯一入口，而 D7 要修「顺序重启丢失」。两者不能同时成立。
建议：**D7 收缩为「DataSourceChain 动态读取 + 顺序确定」**（`NirikoApplication.kt:432` 的列表快照改为 live provider，并补单测）；**删除持久化与 UI 部分**，由 X2 一并删掉 `activeDataSourceId`。这样「重启顺序丢失」的问题自然消失（因为没有可调的顺序了）。若以后要做源优先级，再单开卡。

**裁决 2：单卷漫画（MANGA）是否也隐藏卷进度？**
你原话是「书籍单本不应该有卷进度」。在 Niriko 里漫画属于书籍类型，单卷漫画同样是「单本」。
建议：**统一按「BOOK 类型且卷数 ≤ 1」隐藏，不区分漫画/文字书**；多卷合集保留。规则写成一个纯函数，避免两套判据（现在详情页已有 `series == false` 旧判据，要合并）。

**裁决 3：两条范围外发现是否进批次 A？**

## 4. A-D8 私密收藏被远端覆盖（Lead 补卡）

- **问题**｜本地标了「私密」的收藏，在一次下载合并后变回公开：合并只按下标/行覆盖，没有把 `isPrivate` 当独立字段保护；导出侧又恰好**排除**私密项，于是远端永远是「非私密」，一合并就把本地标记洗掉。
- **改哪里**｜`data/sync/SyncManager.kt` 的 `mergeCollections`（:95、:202 附近）字段级合并；`data/sync/SyncMergePolicy.kt`。
- **怎么改**｜①`isPrivate` 采用「本地为真则保持为真」的单向规则（远端无法取消本地私密，只能本地自己取消）；②为这条规则加一处注释与单测；③D3 改字段级合并时把这条一起实现，不要写成两次逻辑。
- **测试**｜`mergeCollections` 单测：本地私密 + 远端非私密 → 仍私密；本地非私密 + 远端私密 → 私密（取并集）；两侧都非私密 → 非私密。
- **验收**｜标一条私密 → 同步 → 另一台设备拉取 → 该条仍显示私密；导出与 WebDAV 仍排除它。
- **风险/回滚**｜取并集意味着「一台设备取消私密、另一台不同步」时无法传播取消 —— 这是有意的保守选择；要取消私密必须两侧都同步一次。
- **预估**｜S｜**依赖**｜A-D3
