## 13.1 逐条详解

### 13.1 标题 logo 替代文字标题
- **现状**｜无｜TMDb 的图片响应里 **logos 已经反序列化但全仓无人使用**（`data/remote/tmdb/dto/TmdbDtos.kt:183` 的 `TmdbImagesDto.logos`；`data/repository/TmdbRepository.kt:84,93` 只取 posters/backdrops）；详情页标题是纯文字（`ui/subject/DetailSectionId.kt:43` 的 `TITLE` 区块）。
- **提升**｜(a) 用户：详情页首屏显示作品**原版 logo**（日文/中文），辨识度和「作品感」显著提升，而不是一行黑体字；(b) 工程：数据层几乎零成本（响应里已有 logos，语言参数也已配好 `include_image_language=zh,ja,en,null`），工作量集中在纯函数 + 一处渲染 + 单测，与本仓库「计算器可单测」的约定一致。
- **原理**｜四层：①**选图**（语言优先：界面语言 → 原语言；中文时区域 CN > TW > HK；同语言按 `vote_average` 降序再 `vote_count`；跳过 `.svg` 与 `aspect_ratio = 0`；无语言 logo 默认不用，但中文缺失时可回落原语言并写进单测）。②**尺寸框**（面积恒定：`面积 = 2.19 × h²`，`h ≤ 2 × 标题行高`，`w ≤ 3.38 × h` 且不超过原标题宽 —— 只保留规则，数字按详情页标题字号重算并写注释，不要照抄 TV 的 dp 表）。③**对比度**（第一版只做「黑白灰翻到另一头 + 看不清回退文字」，APCA 与柔光后置，因为详情页本身有模糊封面墙当底）。④**回退**（加载中占位高 = logo 框高，避免跳版；失败回文字；`reduceMotion` 下不做交接等待）。
- **效果**｜详情页标题区显示作品 logo，高度不跳动；设置三档「关 / 始终 / 看不清时显示文字」，**默认关**；书籍 / 游戏 / 音乐没有 logo，仍是文字标题（覆盖率不吹）。
- **参考**｜`GrahamZen/izuko-tv@main` 的 `TvTitleLogo.kt` / `TvTitleLogoBox` / `TvTitleLogoContrast.kt` / `TvTitleLogoBitmaps.kt` / `TmdbTitleLogoPickTest` `[码·计划 §7]`（AGPL，**只提炼行为，不抄代码**）；本项目 `TmdbImageSelection.sortPosters` 已是「多语言选图纯函数 + 回归注释」的模板 `[码]`。
- **成本/风险**｜M｜中文 logo 覆盖率天然低于日文；TMDb 图片对象是否带 `iso_3166_1` 未验证（无 key 无法实测），若没有则简繁优先要另找信号。
- **优先级**｜**P0**

### 13.2 同步「预览 + 勾选 + 演练」面板
- **现状**｜部分｜`data/sync/bangumi/BangumiSyncPlan.kt` 已有 `localOnly / remoteOnly / conflict / match` 四类差异，`BangumiSyncPlanner` 能算、`BangumiSyncPriority` 能定优先级；但界面只能「一键同步」，**看不到将发出什么请求**，也不能逐条勾选方向。
- **提升**｜(a) 用户：同步前先看一遍「会发生什么」，逐条决定保留哪边，确认后再执行；(b) 工程：把 7.4（冲突提示）与 7.12（冲突可视化）一次做完，且复用已有纯函数，不动数据层。
- **原理**｜五个页签（差异 / 待确认匹配 / 远端独有 / 日志 / 演练结果）：差异页按条目列「本地：看过 8 分 / 远端：在看」，每行一个方向选择器；**演练模式**把每条将发出的请求（URL + 表单字段 + 静态检查项）完整列出且**不真写**，结果可复制 / 导出 JSON；写入间隔 1.2s、翻页 0.8s（防 429 与验证码）；短评同步**默认关闭**（写错不可逆）。
- **效果**｜设置 → 同步与备份 →「预览并演练」：先看差异 → 勾方向 → 看演练 → 点「执行」；执行后给出「本次合并摘要」。
- **参考**｜`XxkumaXia/douban-bangumi-sync@main`（MIT，59 个文件）的「扫描→匹配→差异→勾选→演练→执行」流程 `[README]`；本项目 `BangumiSyncPlan` / `SyncMergePolicy` `[码]`。
- **成本/风险**｜M｜豆瓣**写回**涉及 ToS 与不可逆，本轮只做「读入 + 本仓库侧同步」的预览；写回单独拍板。
- **优先级**｜**P1**

### 13.3 豆瓣自检端点 + 读写限流档
- **现状**｜部分｜`data/probe/` 已有灰通道连通性自检（HTTP 状态 / 耗时 / 最终 URL / Content-Type / 前若干字节），`util/SourceRateLimiter` 已接 IGDB 4 req/s、MusicBrainz 1 req/s、VNDB 200 次/5min；**豆瓣没有接限流档**。
- **提升**｜用户：豆瓣剧照通道坏了能立刻看出是哪条链路、该换端点还是关掉；工程：把「探测 → 建议 → 限流」串成一条可复用的诊断路径。
- **原理**｜在现有 probe 输出上增加「端点选择 + 建议动作」（换反代 / 关通道 / 降低频率）；限流档按源声明（QPS + 退避），失败走 `RefreshCoordinator` 的 `RetryLadder`。
- **效果**｜设置 → 数据源 → 豆瓣：`连通 1/3 链路 · 建议切换到 frodo 端点`；限流档 `正常 / 保守`。
- **参考**｜dbsync 的「接口自检 + 写入间隔」`[README]`；本项目 `data/probe/` `[码]`。
- **成本/风险**｜S｜豆瓣是灰通道，任何建议都要带「未授权抓取，仅个人查看」的既有声明。
- **优先级**｜P1

### 13.4 应用内更新（v1.2.1 只做检查 + 跳浏览器）

- **状态**｜✅ 做，但**范围缩小**：不下载 APK、不申请安装权限；检查到新版本后打开 GitHub Releases 页面。完整「下载 + 校验 + 调系统安装器」留待以后（见 `release-v1.2.1-plan.md` §8 待办池）。
- **现状**｜无｜仓库根目录直接放 APK（`Niriko-v1.2.0.apk`），更新源天然存在，但 App 内没有任何更新检查入口。
- **提升**｜用户：不用去 GitHub 手动找新版本；工程：把「查版本 → 比较 → 提示」做成纯函数（版本比较可单测），不含任何安装逻辑。
- **原理**｜查 GitHub Release（直连不可用则走镜像列表）→ 语义化版本比较 → 提示更新日志 → 点「去下载」用系统浏览器打开 Releases 页面。**本轮不做**：APK 下载、sha256 校验、`REQUEST_INSTALL_PACKAGES`、FileProvider 安装。
- **效果**｜设置 → 关于 →「检查更新」；有新版本时关于页顶部一条横幅（可忽略该版本）。
- **参考**｜`GrahamZen/izuko-tv@main` 的 `UpdateManager` / `GitHubDownloadMirrors` `[README·计划 §3]`（AGPL，只学流程）。
- **成本/风险**｜S｜版本比较与 URL 拼接是纯函数；风险：GitHub 直连失败时提示要说清楚（给镜像链接），不要让用户以为「已是最新」。
- **优先级**｜P2

### 13.5 首启连通性自检 + 镜像建议（v1.2.1 决定不做）

- **状态**｜❌ 不实施 —— 保持「设置里手动切换端点」的现状，不做首启自动探测。原因：本轮你明确不需要。以下字段仅存档。
- **现状**｜部分｜设置里可切「官方 / 国内反代」端点，切换即时生效；但**首次打开不会自动检测**，用户要自己试出哪个能用。
- **提升**｜用户：第一次装完就自动选到最快线路，不会一打开就转圈；工程：复用 `data/probe/`，成本极低。
- **原理**｜首启（或换网络后）并发探测 3 个端点的小请求（2s 超时）→ 按成功率与耗时选默认 → 全失败则保留原选择并显示「可手动切换」；结果缓存 24 小时，避免每次启动都探测。
- **效果**｜第一次打开时一句「已自动选择最快的线路」，不打断进入；设置里保留手动切换与「重新检测」。
- **参考**｜izuko 的 `BangumiMirror*` 一组 `[README·计划 §3]`；本项目 `data/probe/` 与端点切换 `[码]`。
- **成本/风险**｜S｜探测本身要极轻（HEAD 或 16 字节 Range），否则首启变慢。
- **优先级**｜已撤回（原 P2）

### 13.7 动效判据（可检查清单，不是功能）
- **现状**｜部分｜已有 `ui/animation/NirikoMotionSpecs.kt` 六档弹簧；但 12 域发现 11 处「该走 spec 却内联字面量」、6 处 reduceMotion 漏网、错峰入场实际未生效。
- **提升**｜用户：动效不再有「塑料感」（匀速淡入、无过冲、无静止段）；工程：把审美变成**可检查的断言**，评审时有据可依。
- **原理**｜四条判据：①每个转场边界必须至少有一个视觉元素「活下来」（结构断言：边界两侧共享元素 id 集合非空）；②禁止无意义的 `opacity 0→1` 与线性匀速；③位移/缩放必须二阶弹簧、有阻尼与过冲；④长序列必须有静止段（否则节奏平）。落地方式：JVM 单测断言「时间 → 数值」，不做像素比对（本仓库已证伪离屏光栅化）。
- **效果**｜看不见，但 `plans/` 多一份判据清单，12 域的 11 处不一致有了统一裁决标准。
- **参考**｜onetake 的 carry score 与 motion-web 的反塑料感清单 `[README·计划 §4]`（两者许可都不允许搬代码）。
- **成本/风险**｜S｜判据过严会把「刻意的例外」（dock 手感参数）也判成错，必须配例外清单。
- **优先级**｜P3

### 13.8 特效候选（四选一）
- **现状**｜无｜`ui/animation/` 有 CRT 与半调网点，但没有物理类动效。
- **提升**｜用户：一个「记得住」的细节，用于发布/演示；工程：物理步进是纯函数，符合本仓库单测约定。
- **原理**｜四个候选，按成本排：①**定格阶梯抖动（11Hz 硬切）** —— 与已有 CRT 模式天然一对，时间函数可单测，小改；②**Verlet 绳排** —— 统计页标签词云的物理化，列间零水平约束，指针掠过像撩帘；③**粘性叠层** —— 作品库「叠层书脊」视图，后屏骑压前屏，属于新视图，偏大；④**滚轮视差轨道** —— 平板/折叠屏的横向海报轨道，中等。**不建议**：WebGL2 墨线群（Android 侧要 AGSL/RuntimeShader，而 Robolectric 下 SkSL 编译失败，只能真机验收）。
- **效果**｜选①的话：动画详情页在 CRT 模式下多一层「定格抖动」质感；选②的话：词云可以被手指「拨动」。**只做一个**，不要四个都上。
- **参考**｜`feitangyuan/motion-web@main`（CC BY-NC 4.0，84 个文件）的 `char-curtain` / `press-stack` / `wheel-rail` 案例 `[README·计划 §4]`。
- **成本/风险**｜M｜物理参数需要真机调；与 reduceMotion 的交互必须先定义（关闭时直接静态）。
- **优先级**｜P3

### 13.9 发布片生产线（工具链，不是 App 功能）
- **现状**｜无｜仓库有 `screenshot/` 与 `docs/*prototype.html`，但**没有**一条能放进 README 或发布页的演示片。
- **提升**｜给项目一个 30–60 秒的「一镜到底」演示片，用于发布与 README。
- **原理**｜按 onetake 的产线：把参考片拆成数字 → 选概念 → **节拍表**（镜头长短相差 ≥4×，每个边界写明什么活下来）→ 一个 HTML + 动作库 + 真实运动模糊（180° 快门多采样在线性光下平均）→ 按事件配音 → oracle 自动验收（carry score）。**本机缺 ffmpeg 与 playwright**，这是一次要装工具的独立任务。
- **效果**｜`docs/demo.mp4` + README 顶部一段 webm。
- **参考**｜`feitangyuan/onetake@main`（PolyForm Noncommercial，不可并入 MIT 仓库，只当外部工具用）`[README·计划 §4]`。
- **成本/风险**｜L（依赖工具链）｜非商用许可；生成的片子是产出物、不构成代码衍生，但商业用途要另议。
- **优先级**｜P4（独立任务，与 App 版本无关）
