## 1. 目标与原则

本方案将用户清单拆成可独立交付的阶段。每阶段采用“定位 → 最小实现 → 自动化测试 → 真机验收 → 回归记录”的闭环。

### 1.1 总体目标

1. 修复导航、共享元素、底部 Dock、详情横滑中的确定性体验问题。
2. 修正 AniList、Steam、VNDB、放送日历、漫画进度和剧集数据的语义与绑定准确性。
3. 让详情页数据本地优先：二次进入、重建 ViewModel、进程重启和离线时可复用已成功数据。
4. 增加详情配置、评价合并、作品分区和低风险视觉反馈，同时不破坏收藏、同步、备份和降级能力。

### 1.2 不变约束

- 当前工作区存在大量未提交修改。实施前必须记录基线，不使用 reset、checkout 或批量格式化覆盖用户改动。
- 继续使用现有 Application + factory 依赖组装方式；不为单一功能引入新的 DI 框架。
- 纯规则优先抽成无 Android 依赖的 Kotlin 函数，并先写 JVM 单测。
- Room 每次改表都必须增加显式 Migration、schema 测试和旧版本数据测试；禁止 destructive migration。
- 网络数据必须区分成功但为空、请求失败、缓存过期和从未加载。
- 现有 Dock 动效、详情材质渐显、kyant Dock 动效和高分辨率 hero 图是已知取舍，除非真机证据证明它们是根因，否则不整体重写。
- 减少动态效果、低端设备玻璃降级和无障碍设置优先于新增视觉效果。

## 2. 当前基线与已知事实

### 2.1 已有基础，不能重复实现

- SubjectDetailViewModel 已有 ExtendedSnapshot，字段覆盖角色、剧集、评分、AniList/VNDB、TMDb、剧照和豆瓣候选；目前是进程内 TtlCache，不是 Room 持久化。
- EpisodeDetailScreen 已读取 episode.stillUrl；EpisodeRatingRepository 已有 TMDb 季集对齐、评分写入和剧照回填逻辑。因此“单集图片完全没有实现”需要改为检查数据链路、对齐和状态更新。
- NirikoDatabase 当前为 Room v29，已有迁移链，后续扩展必须递增版本。
- BackupManager 已导出外部 ID、每集评分、手动奖项和封面覆盖；作品分区必须加入同一 JSON 备份协议。
- 角色详情出演作品当前是纵向布局；评分区当前是“一张评分卡 + 分布图”，不能按照旧文档假设它仍是评分横滑卡。
- AniList 候选映射当前没有把真实置信度传入 MatchCandidate，因此落入默认 0；候选 externalId 形如 media-{id}，但绑定入口直接按纯数字解析，导致点击无效。
- 旧文档中关于“已取消标题自动绑定”的描述与当前代码可能不一致，实施时必须重新确认自动绑定策略。

## 5. 阶段 1：导航、共享元素与 Dock 稳定性

### 5.1 预测性返回

涉及 AndroidManifest.xml、MainActivity.kt、NirikoNavHost.kt 和现有导航过渡。

执行顺序：

1. 确认 activity-compose、navigation-compose、compile SDK 和 target SDK 的支持边界。
2. 配置平台回调，并验证低版本兼容。
3. 定义返回优先级：打开的局部层先消费，未消费才出栈。
4. 将拖动进度映射到退场缩放和透明度；取消必须恢复稳定状态，完成只出栈一次。
5. 增加开始、取消、完成、重复回调和子 Sheet 打开时返回的状态测试。

验收：Android 13 以上拖动返回有连续预览；取消不闪烁、不残留偏移；Android 12 及以下保持旧行为；返回键和边缘返回语义一致。

### 5.2 详情进入/退出和共享海报

涉及 NirikoNavHost、SubjectDetailScreen、列表卡片及共享元素调用点。

执行顺序：

1. 确认列表、角色页和详情页的共享 key 唯一且生命周期稳定。
2. 检查占位图、真实图、异步尺寸和 crossfade 是否同时改变共享元素尺寸。
3. 为进入和 pop 返回指定稳定的 bounds/transform 规格。
4. 导航切换时避免重复图片请求和同一海报叠加两个动画。
5. 覆盖快速进入、返回、再次进入和慢网络加载。

验收：连续操作 20 次无首帧闪烁、海报不跳到错误位置、返回后的列表卡片只有一份图片。

### 5.3 Dock 卡顿、形变和命中区域

涉及 ui/bottombar 下的拖拽、动画、Tab 组件和 MainPager。

执行顺序：

1. 分别测量跟手和松手阶段帧耗时，不先替换现有动效实现。
2. 跟手阶段使用直接状态同步，松手阶段使用单一 settle 动画。
3. 使用互斥策略取消旧动画；手势取消、页面切换和重新点击都执行明确 reset。
4. 为每个 Tab 使用互不重叠的语义点击区域，重点检查统计按钮。
5. 将拖拽计算、命中测试和 settle 决策抽成纯逻辑测试。

验收：快速左右拖动、拖动后立即点击、跨页点击和重组后 Dock 都回到正确形态；gfxinfo 不出现明显新增长帧。

### 5.4 横滑卡与标题

- 为横滑内容设置固定高度或统一 heightIn，动态文字不能改变轨道高度。
- 主标题允许换行；不能用单行省略截断用户要求完整展示的主标题。
- 测试大字体、窄屏、超长中英文混排。

验收：横滑时轨道高度稳定；标题完整可读且不遮挡海报、评分和返回控件。

## 6. 阶段 2：外部绑定与内容数据正确性

### 6.1 AniList 确定性修复

涉及 SubjectDetailScreen、ProviderBindingSection、SubjectDetailViewModel 和 AniListRepository。

执行顺序：

1. GameItem 映射为 MatchCandidate 时传入真实置信度、匹配原因和查询词；没有评分时显示“未计算”，不能显示 0%。
2. 统一解析 media-{id}、纯数字和带前缀输入；非法 ID 显示可解释错误。
3. 绑定按钮提供 loading、成功、失败和重复点击保护；失败不能清空候选。
4. 推荐只对明确 ID 映射自动绑定，标题搜索只产生候选并由用户确认。
5. 增加 ID 解析、置信度展示、候选点击和绑定失败测试。

验收：指定条目显示真实百分比，点击有效候选均能绑定；绑定后的 ID、标题和详情一致；网络失败不伪装成无候选。

### 6.2 Steam 与 VNDB 匹配

执行顺序：

1. 为失败样本记录 Bangumi 标题、中文标题、罗马字、别名、系列、版本和候选返回值。
2. 统一规范化 Unicode、标点、大小写、括号和副标题，但保留区分续作的数字。
3. Steam 优先使用已知 appid 或人工绑定；候选必须显示版本和平台信息。
4. VNDB 候选显示版本类型、发行名和别名提示，不能只查询单一标题。
5. MANUAL 绑定不可被自动结果覆盖；自动绑定保存方法、置信度和依据。

验收：目标样本找到正确候选；同系列不同作品不互相覆盖；解绑和重新绑定可恢复。

### 6.3 发现简介、历史放送和剧集标题

执行顺序：

1. 发现卡片按中文简介、原文简介、安全短描述的顺序选择；区分无简介和请求失败。
2. 检查长连载返回字段和 mapper，避免类型过滤、截断或字段映射丢失简介。
3. 放送日历按选中月份加载，不以当前月硬限制；保留跨月延续番的起始日期和当前放送日期。
4. 复用现有刷新协调器的 TTL、single-flight 和失败退避。
5. TMDb 只在 Bangumi 标题缺失或明确开启补充时使用；严格按 TV、season、episode 对齐，特别篇无法对齐时保留 Bangumi 标识。

验收：过去月份可显示可获取条目；无简介和网络失败可区分；状态编辑页的分集标题稳定且不覆盖已有正确标题。

### 6.3.1 分集图片专项任务

涉及 [分集页面](../app/src/main/java/com/otakup/niriko/ui/episode/EpisodeDetailScreen.kt)、[分集仓储](../app/src/main/java/com/otakup/niriko/data/repository/EpisodeRepository.kt)、[外部分集补充](../app/src/main/java/com/otakup/niriko/data/repository/EpisodeRatingRepository.kt)及 [详情状态](../app/src/main/java/com/otakup/niriko/viewmodel/SubjectDetailViewModel.kt)。

1. 记录绑定 TV ID、季号、匹配集号、stillPath、最终 URL、写入行数和 UI 接收时间；不得记录密钥。
2. 检查 Bangumi 集表写入与 TMDb updateStillUrl 的并发顺序：更新时目标集必须已存在，网络刷新不得把已补充剧照清空。
3. 将对齐成功的图片和标题按集 ID 写入，并让页面观察最新本地状态，不只保留打开页面时的一次快照。
4. 区分未绑定、尚未加载、对齐失败、来源无图片及图片请求失败，提供相应重试或绑定操作。
5. 验证 TMDb 支持季内索引的作品、长期连载绝对集号和特别篇；有歧义时拒绝自动图片映射，不显示错误剧照。

验收：本地已写入图片在首次补充后无需退页重进即可出现；重启后 URL 可恢复；断网时只有已缓存图片可显示，不能把“已缓存 URL”宣称为离线图片已下载；来源确实无图片时有正确空态。

### 6.4 漫画卷/话进度

执行顺序：

1. 明确动画=集、漫画/书籍=卷或话、游戏=分钟的单位规则。
2. 分别保留 watchedVolumes 与 watchedEpisodes/chapters，不把 31 卷换算为 276 话。
3. 总卷数未知时显示已读卷数，不伪造百分比；总量可靠时允许切换展示单位。
4. 旧数据只保留可证明的原单位，不做不可逆比例换算。
5. 为下限、上限、未知总量、单位切换和完成状态补纯函数测试。

验收：灌篮高手不会以话数作为卷进度分母；编辑、详情、收藏卡和统计页单位一致。

## 7. 阶段 3：ExtendedSnapshot 与 Room 本地优先

### 7.1 快照审计

逐一核对 SubjectDetailUiState 字段：是否写入快照、是否恢复、是否可序列化、是否有 source version/fetchedAt、是否能区分失败和成功空结果、是否属于不可被网络覆盖的用户数据。

重点包括角色、Staff、剧集、评分分布、外部评分、AniList/VNDB/TMDb 绑定与候选、剧照、豆瓣、手动奖项和每集评分。

### 7.2 数据模型建议

优先按来源拆表，而不是把 Compose UI state 序列化为一个不可查询大 JSON：

- subject_detail_cache：subjectId、sourceKey、schemaVersion、fetchedAt、expiresAt、state、errorSummary。
- subject_relation_cache：角色、Staff、关联作品等可独立刷新集合。
- episode_external_cache：剧照、TMDb 标题、季号/集号、来源和对齐状态。
- 已有 Subject、Episode、ExternalRating 和 Binding 表优先复用，避免重复真相。

复杂远程结构若必须 JSON 保存，也必须带来源、版本、时间和失败状态。

### 7.3 实施顺序

1. 先增加 schema 和 DAO，不改变页面。
2. 增加 readLocal、refreshIfNeeded、refresh(force) 三条明确仓储路径。
3. 页面先读本地成功数据，再后台刷新过期来源；无本地数据才显示 loading。
4. 手动绑定、解绑、换季、评分和封面修改只失效相关来源。
5. 进程重启和离线场景使用本地数据；失败时保留旧成功数据并显示过期提示。
6. 增加下一个 Room 版本 Migration，并用旧数据库 fixture 验证数据保留。
7. 最后收窄 TtlCache 职责，避免 Room 与内存缓存各自决定真相。

验收：重建 ViewModel、杀进程、断网打开都能显示上次成功数据；过期缓存先显示旧内容并后台更新；刷新失败不覆盖旧内容；迁移、备份恢复和异常中断测试通过。

回滚：保留旧字段和旧 DAO 读取能力至少一个版本；迁移问题时停止新缓存读取，禁止 destructive migration。

## 8. 阶段 4：悬浮布局、渐隐层与材质统一

### 8.1 角色出演作品横滑

在 CharacterDetailScreen 将纵向作品列表改为固定宽度 LazyRow 或等效横滑卡。统一图片比例、标题高度和无封面状态；保留 shared element、点击语义和返回手势。测试空数据、单项和大量作品。

### 8.2 液态玻璃

复用现有 GlassCard、玻璃强度和低端降级设置，不为每个控件创建独立 RenderEffect。统一标签、搜索按钮、展开背景、海报爱心/评分/状态的 material token。浅色模式使用浅白半透明底并检查对比度。AGSL/RenderEffect 只能以设备截图作为最终验收，Robolectric 只验证结构和状态。

### 8.3 收藏/发现悬浮控件与顶部渐隐

- 用 Box overlay 将控件固定在窗口层，列表内容可延伸到其下方。
- 使用 window inset 和点击测试，防止浮层吞掉第一项或滚动手势。
- 移除发现页“点此强制刷新”文案，保留下拉刷新或明确图标入口。
- Dock 重新点击发现页：非顶部则回顶，已在顶部才刷新；使用 single-flight 防重复请求。
- 顶部渐隐采用独立 Overlay 和连续 alpha/gradient，不使用滚动阈值离散显隐。

验收：滚动时控件位置稳定，无 AppBar 阴影和矩形硬边；第一项完整可点击；浅色、深色、小屏、大字体和减少动态效果下不重叠。

## 9. 阶段 5：详情配置与评价编辑工作流

### 9.1 详情部件显示和排序

建立稳定的 DetailPaneId 与默认顺序。设置保存隐藏集合和排序列表；未知 ID 忽略，新部件追加到默认尾部。核心标题、收藏、返回和保存操作不可隐藏。增加 DataStore round-trip、默认兼容、重复 ID 和迁移测试。

### 9.2 音乐曲目移入状态编辑

复用现有 TrackListSection、碟片分组、逐首勾选和 watchedTrackIds。只在音乐类型显示；取消不写入；保存后详情和编辑页进度一致。大量曲目时使用折叠或分页，避免一次渲染全部。

### 9.3 单集评价合并和均分

设计纯函数处理：无评分集过滤、前后缀格式化、已有合并块识别、0.5/整数舍入。合并块带稳定标记，重复执行不重复追加；保留手写评论；默认不覆盖已有手动评分。写入作品评分前显示预览与确认，并提供仅评论、仅均分或两者模式。

验收：中文、英文、已有前后缀、换行、重复执行、取消和部分分集评分均有测试，舍入边界统一。

## 10. 阶段 6：作品库自定义分区

### 10.1 数据模型

新增 library_folder：id、name、sortOrder、isCollapsed、createdAt、updatedAt。

新增 library_folder_subject：folderId、subjectId、sortOrder、addedAt，联合唯一键。

一部作品可属于多个分区；删除分区只删除关系，不删除 Subject 或 Collection。折叠状态持久化。

### 10.2 实施顺序

1. Entity、DAO、Migration 和索引。
2. Repository/ViewModel 的创建、改名、排序、折叠、加入、移除和批量加入。
3. 收藏页分区导航；分区内沿用现有排序。
4. 分区内允许作品重复出现，但全局批量选择按 subjectId 去重。
5. BackupManager 导出和恢复分区与成员关系。
6. 明确 WebDAV 对新表的同步边界；不能同步时界面必须提示，不得静默丢失。

验收：多分区、排序、折叠、重启、删除分区、备份恢复、批量操作、搜索和标签互不混淆；重复导入备份幂等。

## 11. 阶段 7：轻量动效、触感和彩蛋

### 11.1 低风险反馈

- 评分跨过整数或 0.5 刻度时轻触感，同一刻度不重复。
- 10 分松手时数字短暂放大并金色闪光，仅在松手确认触发。
- 剧集从未全部看过变为全部看过时播放一次从左到右波浪点亮。
- 详情返回列表时传递 subjectId，卡片播放一次约 300ms 淡光扫过，结束后清除状态。

全部反馈接入 reduceMotion 和系统触感设置；触感不能是唯一反馈。

### 11.2 CRT 老电视模式

仅对 2000 年以前且用户开启自动模式的动画详情启用；建议默认关闭或首次说明。效果分层为扫描线、轻微桶形畸变、低强度色散和有限噪点，总时长约 4 秒后恢复静态。不要在滚动每帧创建昂贵 shader，使用可取消的单一 overlay。AGSL 不可用、低端设备或减少动态效果时降级或关闭。真机检查文字清晰度、发热、耗电、旋转和返回取消。

### 11.3 书籍/漫画半调网点

按 SubjectType.BOOK/MANGA 自动启用低强度页面 overlay，其他类型关闭；不能遮挡正文和点击区域。提供总开关或随减少动态效果关闭，不给每张卡创建独立 shader。

## 14. 风险与回滚

### 高风险

- Room 快照迁移错误：先加表和兼容读，在复制数据库上升级，迁移测试覆盖历史版本。
- 自动匹配误绑：默认标题候选人工确认，保存 matchMethod 和 confidence，保留解绑和手动覆盖。
- 玻璃/CRT shader GPU 差异：所有效果必须有静态回退和设置开关。
- 共享元素与预测性返回冲突：先以稳定 pop 为门禁，再接入拖动预览。

### 回滚规则

- UI/动画用设置开关或 feature flag 回退，不删除旧布局。
- 外部匹配停止新的自动写入，不批量删除已有绑定。
- Room 新表可以停止读取但保留数据，禁止回滚为 destructive migration。
- 删除作品分区只删除关系表记录，不触碰作品主表。
- CRT、网点、触感和庆祝动画均可独立关闭。

## 15. 完成定义与首批实施范围

阶段完成必须同时满足：

- 清单对应项已有实现，或明确记录为外部数据缺失。
- 受影响模块覆盖失败、空态、重试和边界条件。
- 编译和全量 JVM 单测通过；失败原因已记录。
- 需要设备验证的项目有设备、系统、设置和结果记录。
- 没有未解释的 Room schema、备份格式或 WebDAV 兼容变化。
- diff 只覆盖当前阶段，能独立回滚。
- 用户可感知变化已记录到发布说明或设置说明。

推荐首批只做：

1. 阶段 0 基线和样本记录。
2. AniList 匹配度、ID 解析和绑定反馈。
3. 剧集剧照、TMDb 标题和历史月份放送的端到端复现。
4. 漫画卷/话进度语义修复。
5. 导航、共享元素和 Dock 的真机复现与必要修复。

首批结束后再固化 Room 快照 schema，避免尚未确认的数据字段直接进入数据库，也避免把视觉彩蛋与数据迁移绑在一起。

## 21. 真机闪退修复与阶段 1 补批记录

设备：`e2ec5ccb`（`2509FPN0BC`，SDK 37，手势导航 `navigation_mode=2`，密度 480 / 3x，状态栏 inset 144px，**导航栏 inset = 0**）。

### 21.1 首装即闪退：Dock 放进窗口捕获层后自引用

- 现象：安装新调试包后启动即闪退，崩溃缓冲反复出现
  `Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR), fault addr 0x70… in tid … (RenderThread)`，
  native 栈在 `android::uirenderer::RenderNode::prepareTreeImpl` ↔
  `skiapipeline::SkiaDisplayList::prepareListAndChildren` 之间递归。
- 根因：为了让预测性返回能揭示父级 Dock，Dock 被移进 `MainPager`，也就是移进了
  `windowKyantBackdrop` 的**捕获层内部**，而它又继续采样同一个 `windowKyantBackdrop` ——
  「窗口 → Dock → 窗口」自引用，捕获层的 RenderNode 树成环，渲染线程在 prepareTree 时栈溢出。
- 修复（换一个无循环的等价折射源）：
  - Dock 只采样旁路的「壁纸层」捕获（`cardGlassBackdrop`，与卡片玻璃同源）；
  - `MainPager` 自己再捕获一层**页内容层**（`rememberLayerBackdrop { drawContent() }`，不含 Dock 自身），
    用 `rememberCombinedBackdrop` 把「壁纸层 + 页内容层」合成后交给底栏。
  - 合成结果与原来的窗口层等价（壁纸 + 页面内容），但采样链上不再包含底栏自己。
  - 真机结果：`am start` 后进程存活（`pidof` 有值），`logcat -b crash -d` 为空。
- 宽屏（EXPANDED）不共用这条路径：竖向 dock 仍在窗口层（捕获层之外，见 `MainActivity`），
  采样 `windowKyantBackdrop` 不构成环；二级路由保留 dock 与「先回 main 再切页」的行为。
  `MainPager` 只在非 EXPANDED 时挂横向胶囊底栏。

### 21.2 预测性返回父页的坐标系统一

- 现象（用户报告）：预测返回预览里的父页比真实父页「更高」，作品库搜索框被顶出屏幕。
- 根因：`MainActivity` 的内容内边距是按 `currentRoute` 分叉的 —— 详情路由用 `top = 0`。
  但手势进行中 `currentRoute` **仍然是详情页**，于是被预览的父页也被套上 `top = 0`，
  整页上移一个状态栏（本机 144px ≈ 48dp），搜索框正好被顶出可视区。
- 第一次尝试（已在真机证伪）：把详情也改成完整 `innerPadding`。这修好了父页，
  却让详情页**双重避让** —— `SubjectDetailScreen` 内部本来就有
  `.statusBarsPadding()`（背景墙延伸到状态栏后、顶栏自行避让），于是顶栏下移了 288px。
- 最终落地：容器对**所有路由**统一施加同一份 systemBars 内边距（不再看 `currentRoute`），
  详情页在**自己的路由内**反向抵消这一份顶部 inset：
  `ui/common/ContentInsets.kt` 的 `Modifier.negateTopInset(top)` 把内容上移 `top` 并把测量高度放大同样的值，
  于是详情页仍铺满整窗；`NirikoNavHost` 通过新参数 `contentTopInset` 拿到容器施加的那一份。
  这样「按正在被组合的目的地取 inset」取代了「按 currentRoute 取 inset」，同类问题不会再出现。

### 21.3 Dock 跳页被中间页拦截（反馈回路）

- 现象（用户报告）：从作品库跳到设置时会被「发现 / 统计」拦截，设置 ↔ 发现的跳转会被「统计」拦截。
- 根因：`LiquidBottomTabs` 里 `currentIndex` 的 `snapshotFlow` 回路同时承担了「同步指示器」和
  「上报 Pager」两件事。Pager 滚动途中 `pagerState.currentPage` 会依次经过中间页，
  这条回路于是把中间页当成用户选择回调 `onTabSelected`，反过来打断正在进行的滚动。
- 修复：回调点唯一化。外部选中态单向流进指示器（只更新 `currentIndex` / `dragTarget`），
  `onTabSelected` 只在 `onDragStopped`（用户真实选择）调用一次。
- 同时避免「同一目标被零速度重启」抹掉 fling 动量：`DampedDragAnimation.animateToValue` 增加
  `animatedTarget` 幂等判断 —— 手势收尾已经用带释放速度的动画接管同一目标时，外部同步流直接返回。

### 22.1 B06 发现页动画卡片不展示简介 —— 已修（根因经线上 API 实测）

- 现象（用户报告）：发现页部分动画类型卡片没有简介，例：航海王、名侦探柯南。
- 排查结论：**不是卡片、也不是 mapper 的问题**。
  - 实测 `GET https://api.bgm.tv/calendar` 返回的条目，`summary` 字段全是**空串**
    （2026-10 抽样 70 条：70 条全空）。同一次核查里 `GET /v0/subjects` 与旧版搜索的 `summary`
    都有值（例：CLANNAD AFTER STORY 的完整中文简介）—— 数据源本身有简介，只是日历接口不给。
  - `SeasonalTrendingRepository` 的两条候选来源里**日历是权威**且同一 id 以日历为准
    （`SeasonalTrendingCalculator.merge` 的既定语义），于是「只在日历里出现」的长连载拿到空简介；
    它们开播于 1999 年，落在兜底检索「今天 −400 天」窗口之外，那条路也补不到。
- 修法（纯函数 + 一次有界请求）：
  - `SeasonalTrendingCalculator.fillBlankFields(items, donors)`：按 id 把检索结果里**非空**的字段
    补进空缺处；已有值绝不覆盖，放送星期与 `confirmed` 仍以日历为准。
  - `SeasonalTrendingCalculator.needsFieldDonors(...)`：只有「类型过滤 + 排序 + 质量门槛 + 截断后
    可能被展示」的条目仍缺简介时，才值得多跑一次检索 —— 看不见的候选不花流量。
  - `SeasonalTrendingRepository`：捐献者优先用**已经在手**的兜底检索结果（免费）；不足时才补一次
    「热门动画检索」（`type=2&sort=heat`，60 条，不带开播窗口，因此能覆盖开播多年的长连载）。
    补全发生在 `select` **之前**，让 `all` 与 `items` 携带同一份字段
    （`applySeasonalLocally` 会在 `all` 上重跑 `select`，否则切类型栏时补上的简介会丢）。
  - 副作用：这条热门检索同样经 `SubjectRepository.search` 落库，属于顺带缓存，不额外写库。
- 测试：`SeasonalTrendingCalculatorTest` 新增 4 例 —— 空串简介被补上、已有值不被覆盖、
  空捐赠者不清空（且不做无意义 copy）、donors 只在必要时请求（含「被质量门槛挡掉的候选不触发请求」）。

### 22.2 B08 《女神异闻录》系列绑不上 Steam —— 已修（根因经线上 API 实测）

- 现象（用户报告）：部分游戏未绑定到 Steam 信息，例：女神异闻录系列。
- 排查结论：**跨语言不是主因，「空格分词」才是**。
  - 实测 `GET store.steampowered.com/api/storesearch?term=…&l=schinese&cc=CN`：
    - 日文「ペルソナ5 ザ・ロイヤル」→ `total: 0`（Steam 商店根本搜不到）；
    - 中文「女神异闻录5 皇家版」→ 命中 app 1687950，`name` =「女神异闻录5皇家版」（**无空格**）。
  - Bangumi 278949（ペルソナ5 ザ・ロイヤル）的 `name_cn` =「女神异闻录5 皇家版」（**有空格**）。

### 24.2 DAO 语义（DetailCacheDao）

三张表共用一个 DAO（同一个关注点：「这次打开，哪些来源已经取过了」）。关键不是能跑 SQL，而是两个语义：

- `putDetail` 记成功（整行覆盖 + 清空失败信息）；`markFailure` **只写失败信息、绝不碰 payload** ——
  断网打开一次不能把上一次成功的结果洗掉；返回受影响行数 0 表示该来源从未成功过，调用方据此决定错误态。
- `invalidateDetail(subjectId, keys)` 按来源失效：手动绑定只失效 vndb，不波及 infobox / TMDb。
- `replaceRelations` 整块替换（先删后写、同一事务）：集合会**变短**（某人被移出制作组），
  逐条 upsert 会把消失的旧行留下来，UI 里就会出现幽灵角色。

### 28.2 F11：底栏重选当前 tab

- 语义（`navigation/TabReselectPolicy.kt`，纯函数）：**只有当前页的 tab 被再次点按**才进入这条路径；
  不在顶部 → 回顶；已在顶部 → 只有声明了刷新语义的页才发请求（发现页），其余页无操作。
- 触发点：`LiquidBottomTabs`（手机横向胶囊）与 `LiquidVerticalDock`（宽屏竖向 dock）
  各自唯一的手势回调 `onDragStopped` —— 原来 `if (targetIndex != selectedTabIndex())` 直接丢掉
  同 tab 的点按，现在**切页仍走 `onTabSelected`，同 tab 改走 `onTabReselected`**（回调点依旧唯一）。
- 事件流：`MainActivity` 持有 `TabReselectSignal(事件号, 页号, 处置)`，两条 dock 形态共用同一入口；
  `NirikoNavHost → MainPager → 各顶层页` 以「值 + 单调事件号」下发，消费层用
  `LaunchedEffect(事件号)` —— **重组不会重复消费**，同一事件可被多个候选容器幂等地读一次
  （切换卡片/宫格/海报布局时旧容器还在组合中，一次性 collect 会吃掉它）。
- 消费点：发现页三个视图（卡片 `TrendingSection`、海报 `DiscoverPosterPane`、宫格 `DiscoverGridPane`）
  各自用**自己那个**滚动状态判决；作品库按当前视图样式（列表/网格/画廊）回顶；统计页回顶。
- 回顶实现：`util/ScrollToTop.kt` —— 近一屏用 `animateScrollBy` 沿真实距离做弹簧滚动，
  更远直接 `scrollToItem(0)`（`animateScrollToItem` 会把长距离压成一帧闪回）。
  已是顶部无条件空操作；动画期间用户按下 → 协程被取消 → 这里**不强行回顶**。
  网格的距离换算拿不到稳定列数，因此只在**还停在第 0 行以内**时才用动画，其余落位。
- single-flight：重选走的是**既有唯一刷新入口** `SubjectSearchViewModel.refreshTrending()` ——

## 30. 阶段 6（F09 作品库自定义分区）

> 本批是**完整的一个功能**（§10）：数据库 → DAO → ViewModel → 界面 → 备份 → 同步边界 → 测试。
> 设备/观感类验收仍由用户在手头设备上复核；本批给出的是「编译 + 全量单测 + 可安装包」。

### 30.1 数据模型（v31 → v32，只加不改）

| 表 | 主键 | 存什么 |
|---|---|---|
| `library_folder` | id（自增） | name / sortOrder / isCollapsed / createdAt / updatedAt |
| `library_folder_subject` | (folderId, subjectId) | sortOrder 保序、addedAt |

- 一部作品可以属于**多个**分区（多对多）——F09 的原文就是「一作多区」。
- 联合唯一键 = 复合主键：重复加入是**幂等**的（REPLACE），不会在分区里出现两张一样的卡。
- `MIGRATION_31_32` **只 CREATE 两张新表 + 两个索引，不动任何既有列** ——
  与 v29→v30 同一个口径：不可能影响用户评分 / 评论 / 手动绑定 / 既有收藏。
  回滚方式同样最简单：停止读新表（表与数据都留着）。
- `subjectId` 单独建索引（反查「这部作品在哪些分区」）；folderId 是复合主键最左列，自带索引，不再重复声明。

### 30.2 DAO 语义（LibraryFolderDao）

- `deleteFolder` = 先删成员、再删分区行，**同一事务**：不会留下指向已删分区的孤儿关系行
  （那会让下次同名分区凭空多出成员）。删除**不触碰 subjects / collections**（§14 回滚条款）。
- `replaceMembers` 整块替换（先清后写）：集合会变短，逐条 upsert 会把消失的旧行留下来变成幽灵。
- `addSubjectAndTouch / removeSubjectAndTouch / addSubjectsAndTouch / removeSubjectsAndTouch`：
  成员变化**必须触碰分区行**（updatedAt 前移）。导航条的成员数来自 `observeFolders()` 这条流，
  它只在分区行变化时发新值 —— 只写关系行就会「加进去了但数字没变」。**这是单测锁住的一条**。
- `clearAllFoldersAndMembers`：清空顺序「先成员后分区」，同一事务。
- `pruneMembersNotInCollections` / `foldersWithOrphanMembers`：见 §30.5 的同步边界。

### 30.3 ViewModel 与界面

- `CollectionFilter` 增加 `folderId`：分区是**筛选维度**而不是「另一份收藏」——
  作品仍来自同一张 collection 表，因此删分区永远不影响收藏本身。
  过滤顺序：状态 → **分区** → 标签 → 排序（分区只决定「哪些作品参与」，不改变排序语义）。
- `CollectionViewModel`：`folders` StateFlow（含成员数与折叠态）、`selectFolder`、`createFolder`
  （Room 分配 id 后回调，界面据此立刻切到新分区）、`renameFolder`、`deleteFolder`（若正在看它则回到「全部」）、
  `setFolderCollapsed`、`moveFolder`（**整表重排**而不是两行交换：中途失败也不会留下两个相同的 sortOrder）、
  `addToFolder`（单个 / 批量，批量先 `distinct()` —— §10.2 第 4 条「全局按 subjectId 去重」）、
  `removeFromFolder`、`folderIdsOf`（弹层显示勾选态）。
  另外 `batchDelete` 删收藏时会**顺手清掉分区成员**（否则成员数会显示一个点进去看不到的作品）。
- 界面（`ui/library/FolderNavBar.kt` + 作品库页）：
  - 分区条**常驻**：没有任何分区时它就是「新建分区」的唯一入口；
  - 点分区 = 进入该分区（写 folderId），再点当前分区 = 回到「全部」（收起）；
  - **长按** = 重命名 / 上移 / 下移 / 收起展开 / 删除分区；
  - 收藏卡长按菜单新增「加入分区…」→ 弹层列出全部分区，点一下在「属于 / 不属于」间切换（加入 / 移出）；
  - 多选批量栏新增「加入分区」→ 一次把所选作品加进去。
- 折叠语义（本批采用的读法，写在代码注释里）：**收起的分区在导航条上只占一个名字**
  （不显示成员数徽标、箭头朝右），展开后显示成员数。点击始终是「进入分区」，切换折叠在长按菜单里。
  这是一条**主观解释**，用户若想要「列表内容折叠」的形式，改的是渲染层、数据层不用动。
- 空名分区：新建/改名都由 `isUsableFolderName`（去空白非空）挡住；显示有 `folderDisplayName` 兜底。

### 30.4 备份（JSON 格式 v3 → v4）

- 导出新增 `libraryFolders`：每个分区带 name / sortOrder / isCollapsed / createdAt / **members（subjectIds）**。
  成员一次性取回再分组，避免「每个分区一次查询」的 N+1。
- **刻意不导出数据库自增 id**：id 换设备/重建库即失效。身份用**分区名**（规范化 = 去首尾空白 + 大小写折叠），
  恢复时按名字找本地分区、找不到就新建。
- 恢复语义与项目既定的 [RestoreMergePolicy] 一致 —— **本地优先**：
  `fullReplace` 先清空再写（备份即现状）；合并模式只新建本地没有的分区，
  **本地同名分区连成员一起保持原样**（否则会把备份里的旧成员掺进用户现在的分区）。
  这条语义由 `BackupFolderNames.foldersToPopulate` 表达，并由单测锁住 ——
  第一批实现里这里写错过一次（同名分区也照写成员），是测试跑出来的。
- 成员只保留「本次备份确实存在的作品」（与其它表同一条防孤儿规则）；空名分区丢弃；成员去重。
- 旧备份（≤ v3）没有这两个字段 → 解析成空列表，导入照常成功（不因为一个新字段让整份备份失败）。

### 30.5 WebDAV 同步边界（§10.2 第 6 条）

- **分区不参与 WebDAV 同步**，只随 JSON 备份迁移 —— 这是有意的取舍：WebDAV 的合并是「整表 LWW」，
  而分区没有跨设备稳定的身份键（自增 id 换设备即失效），强行同步会造出重复分区。
- 「不得静默丢失」的两条落地：
  1. 同步设置页在 WebDAV 区块下**写明**这句话（分区只随备份迁移，换设备请导入备份）；
  2. WebDAV 下载会整体重写 collections 表，因此写完 collection 后立刻
     `pruneMembersNotInCollections` 清掉「已不在收藏里」的成员并触碰对应分区行 ——
     否则同步完成后分区会显示一个点进去看不到的作品。

## 33. 阶段 5 首批（F07 分集评价合并与均分）

### 33.1 落地：纯规则 + 预览弹层

- 新增 `util/EpisodeReviewMergePolicy.kt`（**纯函数**，不碰 Compose 与数据库）：

## 37. 阶段 7 首批（F15 评分刻度触感 · F16 满分松手确认）

> §11.1 的四条轻量反馈里先做这两条：它们落在**同一个控件**（评分滑块）上，

### 37.1 落地

- 新增 `util/RatingFeedbackPolicy.kt`（纯规则）：
  - `tickIndex` / `snapped`：把浮点统一到 0.5 刻度上（比较刻度而不是比较浮点）；
  - `crossesTick`：**同一刻度不重复**这条就落在这里 —— 手指在同一格里来回抖动不触发；
  - `hapticCountFor`：一次变化跨 n 格也只发 **1** 声（快速甩动按格数连响会变成一串噪音）；
  - `shouldCelebratePerfect`：**仅在松手**且这一拖「从非满分进入满分」时为真 ——
    因此打开编辑面板时本来就有的 10 分不会自己闪；
  - `shouldAnimateScale(reduceMotion)`：减少动态效果时不缩放（但颜色反馈仍在）。

## 45. 阶段 1 补批（B03 横滑卡高度抖动 · 收官）

> §17 覆盖表里最后一项待做。做之前先把「实际横滑轨道」找齐（§5.4 的验收就是这句），
> 结论是：**问题不在封面、不在某个特定页面，而在一条被四处违反的不变量**。

### 45.1 先定位：哪些轨道真的会抖

逐个核对 `LazyRow` 的卡片高度是否依赖数据：

| 轨道 | 结论 |
|---|---|
| 详情页 Steam 截图 / 剧照缩略图（220dp × 16:9） | **不抖**：尺寸固定（§28 已记） |
| 统计页日期条 | **不抖**：固定单元 |
| 角色（CharacterStaffSection） | **抖**：角色名与 CV 两行各自被 `if`/`let` 包着 |
| 制作人员（同上文件） | **抖**：角色名条件渲染 |
| 关联条目（RelationsSection） | **抖**：关系标签条件渲染 + 标题 1~2 行 |
| 人物收藏（PersonCollectionSection） | **抖**：职业条件渲染 |
| 人物详情页角色卡 | **抖**：角色名条件渲染 |
| 参与作品卡（`CreditSubjectCard`，F01 新建） | **抖**：副标题「都空时整行不生成」 |

**根因**：`LazyRow` 的高度取当前已组合卡片中**最高**的一张。只要卡片高度依赖数据，
横向滚动把新卡片组合进来时，整条轨道的高度就会变 —— 这就是「横滑时上下抖动」。

### 45.2 落地

- 新增 `util/RailCardPolicy.kt`（纯规则）：`TITLE_LINES` / `WIDE_TITLE_LINES` / `LABEL_LINES`、

  它表达的就是这条不变量：**同一轨道内每张卡固定占同样的行数**。
- 六处轨道卡片按同一手法改：**尾随行无条件渲染**（没有数据就渲染空文本）并给 `minLines = 1`；
  标题用 `minLines = maxLines`（关联条目卡固定两行）。
- **更正 §29 的一处判断**：F01 那批我在 `CreditSubjectCard` 里写的是「副标题两者都空时整行不生成」，
  理由是「空字符串会占出一行高度」—— 那是**反的**：不生成整行才会让这张卡比同轨道其它卡矮一行。
  现在它与其余轨道一致（空值也保留一行），代码注释里也留了这条更正。
